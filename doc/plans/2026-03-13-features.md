# Especificaciones de funcionalidades

## 1) Incorporación guiada + primera tarea mágica

El repo ya tiene `onboard`, `doctor`, `run`, modos de despliegue e incluso texto/endpoints de incorporación orientados a agentes, pero también hay problemas actuales de validación de incorporación/auth y un reporte abierto de "onboard fallido". Eso significa que esto no es solo pulido; es crítico para el producto. ([GitHub][1])

### Decisión de producto

Reemplazar la "incorporación configuración-primero" con **incorporación entrevista-primero**.

### Qué queremos

- Hacer 3–4 preguntas al inicio, no 20 ajustes.
- Generar la ruta correcta automáticamente: local solo, privado compartido o nube pública.
- Detectar qué entorno de agente/tiempo de ejecución ya existe.
- Hacer normal que Claude/OpenClaw/Codex ayuden a completar la configuración.
- Terminar la incorporación con una **primera tarea real**, no un panel en blanco.

### Qué no queremos

- Jerga de proveedores antes del valor.
- "Ve a buscar una API key" como primera instrucción por defecto.
- Una instalación exitosa que aún deja a los usuarios sin saber qué hacer después.

### UX propuesta

En la primera ejecución, mostrar una entrevista:

```ts
type OnboardingProfile = {
  useCase: "startup" | "agency" | "internal_team";
  companySource: "new" | "existing";
  deployMode: "local_solo" | "shared_private" | "shared_public";
  autonomyMode: "hands_on" | "hybrid" | "full_auto";
  primaryRuntime: "claude_code" | "codex" | "openclaw" | "other";
};
```

Preguntas:

1. ¿Qué estás construyendo?
2. ¿Es una empresa nueva, una empresa existente o un equipo de servicio/agencia?
3. ¿Estás trabajando solo en una máquina, compartiendo en privado con un equipo o desplegando públicamente?
4. ¿Quieres full auto, híbrido o control manual estricto?

Entonces Paperclip debería:

- detectar CLIs/proveedores/suscripciones instalados
- recomendar el modo de despliegue/auth correspondiente
- generar un prompt local `onboarding.txt` / de handoff para el LLM
- ofrecer un botón: **“Open this in Claude / copy setup prompt”**
- crear objetos iniciales:

  - empresa
  - objetivo de empresa
  - CEO
  - ingeniero fundador o primer reporte equivalente
  - primera tarea sugerida

### Backend / API

- Agregar `GET /api/onboarding/recommendation`
- Agregar `GET /api/onboarding/llm-handoff.txt`
- Reutilizar los patrones existentes de invitación/incorporación/habilidades para bootstrap local-primero
- Persistir las respuestas de incorporación en la configuración de la instancia para defaults posteriores

### Criterios de aceptación

- Una instalación fresca con un tiempo de ejecución local soportado se completa sin edición manual de JSON/env.
- El usuario ve la primera acción viva de un agente antes de salir de la incorporación.
- Un panel en blanco ya no es el estado default post-instalación.
- Si falta una dependencia requerida, el error es prescriptivo y reparable desde la UI/CLI.

### No-objetivos

- Creación de cuentas
- SSO empresarial
- detección automática perfecta de proveedores para cada tiempo de ejecución

## 2) Superficie de comandos del tablero, no chat genérico

Hay una tensión real aquí: la transcripción dice que los usuarios quieren "chatear con mi CEO", mientras la definición pública de producto dice que Paperclip **no es un chatbot** y la comunicación V1 es **solo tareas + comentarios**. Al mismo tiempo, el repo ya está explorando infraestructura de plugins e incluso un plugin de chat vía streaming SSE de plugins. La resolución limpia es: **hacer conversacional la superficie central, pero mantener el modelo de datos céntrico en tareas/hilos; reservar el chat completo como un plugin opcional**. ([GitHub][2])

### Decisión de producto

Construir un **composer de comandos** respaldado por issues/comentarios/aprobaciones, no un subsistema separado de chat.

### Qué queremos

- La sensación de "hablar con el CEO" para el usuario.
- Cada conversación termina adjunta a un objeto real de la empresa.
- La discusión de estrategia puede producir issues, artefactos y aprobaciones.

### Qué no queremos

- Una pantalla de inicio en blanco de "chatea con IA" desconectada de la organización.
- Otro producto más de chat con agentes.

### UX propuesta

Agregar un composer global con modos:

```ts
type ComposerMode = "ask" | "task" | "decision";
type ThreadScope = "company" | "project" | "issue" | "agent";
```

Ejemplos:

- En el panel: "Pedir al CEO un plan de contratación" → crea un issue/hilo `strategy` con alcance de empresa.
- En la página del agente: "Decir al diseñador que lo haga más limpio" → agrega un comentario de instrucción a un issue o genera una nueva tarea delegada.
- En la página de aprobación: "¿Por qué pides contratar?" → agrega un comentario del tablero al contexto de la aprobación.

Agregar tipos de issue:

```ts
type IssueKind = "task" | "strategy" | "question" | "decision";
```

### Backend / modelo de datos

Preferir extender los `issues` existentes en lugar de crear `chats`:

- `issues.kind`
- `issues.scope`
- opcional `issues.target_agent_id`
- metadatos de comentario: `comment.intent = hint | correction | board_question | board_decision`

### Criterios de aceptación

- Un usuario puede "preguntar al CEO" desde el panel y recibir una respuesta en un hilo con alcance de empresa.
- Desde ese hilo, el usuario puede crear/aprobar tareas con un clic.
- No se requiere una base de datos de chat separada para v1 de esta funcionalidad.

### No-objetivos

- UX de chat de consumidor
- marketplace de modelos
- asistente de propósito general sin relación con el contexto de la empresa

## 3) Visibilidad viva de la organización + capa de explicabilidad

La promesa central del producto ya es visibilidad y gobernanza, pero ahora mismo la transcripción deja claro que la UI aún está demasiado cerca de la ejecución cruda de agentes. El repo ya tiene organigramas, actividad, ejecuciones de latido, costos y superficies de detalle de agentes; la pieza que falta es la capa explicativa sobre ellos. ([GitHub][1])

### Decisión de producto

Por defecto la UI muestra **resúmenes operativos legibles para humanos**, con los registros crudos una capa abajo.

### Qué queremos

- A nivel de empresa: "quién está activo, qué están haciendo, qué se está moviendo entre equipos"
- A nivel de agente: "cuál es el plan, qué paso está completo, qué salidas se produjeron"
- A nivel de ejecución: "primero el resumen, segundo la transcripción"

### UX propuesta

Página de empresa:

- organigrama con indicadores vivos de estado activo
- animación de delegación entre nodos cuando el trabajo se mueve
- prioridades abiertas actuales
- aprobaciones pendientes
- franja de advertencia de consumo / presupuesto

Página de agente:

- tarjeta de estado
- issue actual
- lista de verificación del plan
- último(s) artefacto(s)
- resumen de la última ejecución
- traza/registros crudos expandibles

Página de ejecución:

- **Resumen**
- **Pasos**
- **Transcripción cruda / llamadas de herramientas**

### Backend / API

Generar un modelo de vista de ejecución desde los datos actuales de ejecución/actividad:

```ts
type RunSummary = {
  runId: string;
  headline: string;
  objective: string | null;
  currentStep: string | null;
  completedSteps: string[];
  delegatedTo: { agentId: string; issueId?: string }[];
  artifactIds: string[];
  warnings: string[];
};
```

La Fase 1 puede derivar esto del lado del servidor desde los registros/comentarios de ejecución existentes. Persistir solo si se necesita más tarde.

### Criterios de aceptación

- El tablero puede saber qué está pasando sin leer comandos shell.
- Los registros crudos siguen accesibles, pero no son la superficie default.
- Los momentos de primera tarea / primera contratación / primera completitud se celebran visiblemente.

### No-objetivos

- sistema de animación sobrediseñado
- resumen semántico perfecto antes de que exista la calidad central de datos

## 4) Sistema de artefactos: adjuntos, explorador de archivos, vistas previas

Esta brecha ya se está mostrando en el repo. El almacenamiento está presente, los endpoints de adjuntos existen, pero los issues actuales muestran que los adjuntos aún son efectivamente céntricos en imágenes y el renderizado de adjuntos de comentarios está incompleto. Al mismo tiempo, tu transcripción quiere planes, docs, archivos y páginas web generadas expuestas limpiamente. ([GitHub][4])

### Decisión de producto

Introducir un modelo **Artefacto** de primera clase que unifique:

- archivos subidos/generados
- archivos de workspace de interés
- URLs de vista previa
- docs/reportes generados

### Qué queremos

- Planes, specs, CSVs, markdown, PDFs, logs, JSON, salidas HTML
- fácil descubrimiento desde las páginas de issue/ejecución/empresa
- un explorador de archivos ligero para workspaces de proyecto
- enlaces de vista previa para sitios/apps generados

### Qué no queremos

- obligar a los agentes a pegar todo inline en los comentarios
- HTML metido en cuerpos de comentarios como workaround
- un IDE web completo

### Fase 1: corregir las brechas obvias

- Aceptar tipos MIME no-imagen para adjuntos de issues
- Adjuntar archivos a comentarios correctamente
- Mostrar metadatos de archivos + descargar/abrir en la página del issue

### Fase 2: introducir artefactos

```ts
type ArtifactKind = "attachment" | "workspace_file" | "preview" | "report_link";

interface Artifact {
  id: string;
  companyId: string;
  issueId?: string;
  runId?: string;
  agentId?: string;
  kind: ArtifactKind;
  title: string;
  mimeType?: string;
  filename?: string;
  sizeBytes?: number;
  storageKind: "local_disk" | "s3" | "external_url";
  contentPath?: string;
  previewUrl?: string;
  metadata: Record<string, unknown>;
}
```

### UX

La página del issue obtiene una sección **Entregables**:

- Archivos
- Reportes
- Enlaces de vista previa
- Último artefacto generado destacado arriba

La página del proyecto obtiene una pestaña **Archivos**:

- árbol de carpetas
- cambios recientes
- atajo "Abrir archivos producidos"

### Manejo de vistas previas

Para salidas HTML/estáticas:

- despliegue local → abrir URL de vista previa local
- despliegue compartido/público → hospedar vía servicio de vista previa configurado o almacenamiento estático
- la URL de vista previa se registra de vuelta en el issue como artefacto

### Criterios de aceptación

- Los agentes pueden adjuntar `.md`, `.txt`, `.json`, `.csv`, `.pdf` y `.html`.
- Los usuarios pueden abrirlos/descargarlos desde la página del issue.
- Un sitio estático generado puede abrirse desde un issue sin cazar por el filesystem.

### No-objetivos

- IDE de navegador
- editor colaborativo de docs
- UI completa de administración de object-storage

## 5) Despliegue compartido/en la nube + tiempos de ejecución en la nube

El repo ya tiene una historia clara de despliegue en docs: `local_trusted`, `authenticated/private` y `authenticated/public`, más guía de Tailscale. El roadmap explícitamente menciona agentes en la nube como Cursor / e2b. Eso significa que el próximo paso no es inventar un modelo de despliegue; es hacer canónico y usable en producción el camino compartido/en la nube. ([GitHub][5])

### Decisión de producto

Hacer **despliegue privado/compartido** y **despliegue público/en la nube** modos soportados de primera clase, y agregar **drivers de tiempo de ejecución remoto** para agentes ejecutados en la nube.

### Qué queremos

- una instancia que un equipo realmente pueda compartir
- una ruta local-first que suba a privado/público sin un cambio de modelo mental
- ejecución remota de agentes para tiempos de ejecución no locales

### Arquitectura propuesta

Separar el **plano de control** del **tiempo de ejecución** más explícitamente:

```ts
type RuntimeDriver = "local_process" | "remote_sandbox" | "webhook";

interface ExecutionHandle {
  externalRunId: string;
  status: "queued" | "running" | "completed" | "failed" | "cancelled";
  previewUrl?: string;
  logsUrl?: string;
}
```

Primer driver remoto: `remote_sandbox` para ejecución estilo e2b.

### Entregables

- recetas canónicas de despliegue:

  - local solo
  - privado compartido (Tailscale/auth privada)
  - nube pública (Postgres gestionado + object storage + URL pública)

- página de salud del tiempo de ejecución
- matriz de capacidades de adaptador/tiempo de ejecución
- una ruta oficial de despliegue de referencia

### UX

Nueva página de ajustes "Deployment":

- modo de instancia
- auth/exposición
- estado de almacenamiento/base de datos
- drivers de tiempo de ejecución configurados
- verificaciones de salud y alcanzabilidad

### Criterios de aceptación

- Dos humanos pueden iniciar sesión en una instancia authenticated/private y usarla concurrentemente.
- Un despliegue público puede ejecutar agentes vía al menos un tiempo de ejecución remoto.
- `doctor` detecta configuración pública/privada faltante y da correcciones concretas.

### No-objetivos

- Paperclip SaaS totalmente gestionado
- cada posible proveedor de nube en v1

## 6) Colaboración multi-humana (mínima, no RBAC empresarial)

Esta es la mayor desviación deliberada de la spec actual de V1. Públicamente, V1 aún dice "operador del tablero humano único" y pone la granularidad de roles humanos fuera de alcance. Pero la transcripción acierta en que el uso compartido es necesario si Paperclip va a ser real para equipos. La clave es hacer un **modelo mínimo de colaboración**, no un sistema gigante de permisos. ([GitHub][2])

### Decisión de producto

Enviar **membresías de empresa multi-usuario gruesas**, no RBAC empresarial de grano fino.

### Roles propuestos

```ts
type CompanyRole = "owner" | "admin" | "operator" | "viewer";
```

- **owner**: propiedad de instancia/empresa, invitaciones de usuarios, configuración
- **admin**: gestionar organización, agentes, presupuestos, aprobaciones
- **operator**: crear/actualizar issues, interactuar con agentes, ver artefactos
- **viewer**: solo lectura

### Modelo de datos

```ts
interface CompanyMembership {
  userId: string;
  companyId: string;
  role: CompanyRole;
  invitedByUserId: string;
  createdAt: string;
}
```

Objetivo stretch más tarde:

- alcance opcional de proyecto/equipo

### Qué queremos

- panel compartido para equipos reales
- atribución de usuario en el registro de actividad
- flujo simple de invitación
- aislamiento a nivel de empresa preservado

### Qué no queremos

- ACLs por campo
- consolas de admin empresarial SCIM/SSO
- diez toggles de permisos por página

### Criterios de aceptación

- Un equipo de 3 puede usar una instancia compartida de Paperclip.
- Cada acción de usuario está atribuida correctamente en la actividad.
- Los límites de membresía de empresa se aplican.
- El viewer no puede mutar; el operador/admin sí.

### No-objetivos

- RBAC empresarial
- permisos matriciales entre empresas
- lógica de gobernanza multi-tablero en el primer corte

## 7) Modo auto + interrumpir/reanudar

Este es un tema de comportamiento de producto, no un detalle de UI. Si los agentes no pueden seguir trabajando o aceptar corrección de rumbo sin reiniciar, el modelo de autonomía se siente falso.

### Decisión de producto

Hacer el modo auto y la interrupción a mitad de ejecución semánticas de tiempo de ejecución de primera clase.

### Qué queremos

- Modo auto que continúa hasta bloquearse por aprobaciones, presupuestos o pausa explícita.
- Corrección a mitad de ejecución tipo "te perdiste esto" sin perder continuidad de sesión.
- Estado claro cuando un agente está esperando, bloqueado o pausado.

### Modelo de estado propuesto

```ts
type RunState =
  | "queued"
  | "running"
  | "waiting_approval"
  | "waiting_input"
  | "paused"
  | "completed"
  | "failed"
  | "cancelled";
```

Agregar interjecciones del tablero como eventos de entrada reanudables:

```ts
interface RunMessage {
  runId: string;
  authorUserId: string;
  mode: "hint" | "correction" | "hard_override";
  body: string;
  resumeCurrentSession: boolean;
}
```

### UX

Botones en la ejecución activa:

- Pausa
- Reanudar
- Interrumpir
- Abortar
- Reiniciar desde cero

Interrumpir abre un pequeño composer que dice explícitamente:

- continuar la sesión actual
- o reiniciar la ejecución

### Criterios de aceptación

- Un comentario del tablero puede reanudar una sesión activa en lugar de generar una fresca.
- El ID de sesión permanece estable para la ruta "continuar".
- La UI distingue claramente bloqueado vs. esperando vs. pausado.

### No-objetivos

- edición viva simultánea multi-usuario de la misma transcripción de ejecución
- UX conversacional perfecta antes de que la semántica de tiempo de ejecución esté corregida

## 8) Seguridad de costos + endurecimiento de latido/tiempo de ejecución

Este es probablemente el workstream inmediato más importante. La transcripción dice que el consumo de tokens es el mayor dolor, y el repo actualmente tiene issues activos alrededor de evidencia de aplicación de presupuesto, validación de incorporación/auth y prevención de desperdicio estilo circuit-breaker. Los docs públicos ya prometen presupuestos duros, y el tracker de issues está apuntando a las protecciones operativas faltantes. ([GitHub][6])

### Decisión de producto

Tratar esto como un **contrato de tiempo de ejecución P0**, no un nice-to-have.

### Parte A: gating determinista de despertares

Hacer detección barata y explícita de trabajo antes de invocar un LLM.

```ts
type WakeReason =
  | "new_assignment"
  | "new_comment"
  | "mention"
  | "approval_resolved"
  | "scheduled_scan"
  | "manual";
```

Reglas:

- si no existe entrada accionable nueva, no llamar al modelo
- el scan programado debería ser primero una verificación barata de política, no un pase completo de razonamiento

### Parte B: contrato de presupuesto

Mantener la promesa pública existente, pero hacerla innegable:

- advertencia al 80%
- pausa automática al 100%
- rastro de auditoría visible
- override explícito del tablero para continuar

### Parte C: circuit breaker

Agregar guardas de tiempo de ejecución por agente:

```ts
interface CircuitBreakerConfig {
  enabled: boolean;
  maxConsecutiveNoProgress: number;
  maxConsecutiveFailures: number;
  tokenVelocityMultiplier: number;
}
```

Disparar cuando:

- sin progreso de issue/estado/comentario por N ejecuciones
- N fallas seguidas
- pico de tokens vs promedio móvil

### Parte D: refactorizar el servicio de latidos

Dividir la orquestación actual en módulos:

- detector de despertares
- gestor de checkout/bloqueos
- ejecutor de adaptadores
- gestor de sesiones
- registrador de costos
- evaluador de breaker
- streamer de eventos

### Parte E: suite de regresión

Pruebas automáticas obligatorias para:

- matriz de incorporación/auth
- comportamiento de presupuesto 80/100
- sin fuga de auth entre empresas
- comportamiento idle sin despertares espurios
- reanudar/interrumpir ejecución activa
- smoke de tiempo de ejecución remoto

### Criterios de aceptación

- Una organización idle sin trabajo nuevo no genera llamadas al modelo desde scans de latido.
- 80% muestra solo advertencia.
- 100% pausa el agente y bloquea la ejecución continua hasta el override.
- La pausa del circuit breaker es visible en auditoría/actividad.
- Los módulos de tiempo de ejecución tienen contratos explícitos y son testeables independientemente.

### No-objetivos

- optimización autónoma perfecta
- eliminar todas las llamadas desperdiciadas en cada adaptador/proveedor

## 9) Workspaces de proyecto, vistas previas y handoff de PR — sin convertirse en GitHub

Esta es la forma correcta de resolver el debate del flujo de código. El repo ya tiene instancias locales a worktree, `workspaceStrategy.provisionCommand` de proyecto y un RFC para aislamiento de git worktree a nivel de adaptador. Esa es la dirección arquitectónica correcta: **políticas de ejecución de proyecto y aislamiento de workspace**, no revisión de PR integrada. ([GitHub][7])

### Decisión de producto

Paperclip debería gestionar el ciclo de vida **issue → workspace → vista previa/PR → handoff de revisión**, pero dejar diffs/revisión/merge a herramientas externas.

### Config propuesta

Preferir configuración de proyecto local al repo:

```yaml
# .paperclip/project.yml
execution:
  workspaceStrategy: shared | worktree | ephemeral_container
  deliveryMode: artifact | preview | pull_request
  provisionCommand: "pnpm install"
  teardownCommand: "pnpm clean"
  preview:
    command: "pnpm dev --port $PAPERCLIP_PREVIEW_PORT"
    healthPath: "/"
    ttlMinutes: 120
  vcs:
    provider: github
    repo: owner/repo
    prPerIssue: true
    baseBranch: main
```

### Reglas

- Para proyectos no-código: `deliveryMode=artifact`
- Para trabajo de UI/app: `deliveryMode=preview`
- Para proyectos de ingeniería respaldados por git: `deliveryMode=pull_request`
- Para proyectos respaldados por git con `prPerIssue=true`, un issue se mapea a una rama/worktree aislada

### UX

La página del issue muestra:

- enlace/estado del workspace
- URL de vista previa si está disponible
- URL del PR si se creó
- botón "Reabrir vista previa" con TTL
- ciclo de vida:

  - `todo`
  - `in_progress`
  - `in_review`
  - `done`

### Qué queremos

- trabajo paralelo seguro de agentes en un repo
- salida visible en vista previa
- revisión externa de PR
- hooks definidos por el proyecto, no suposiciones hardcodeadas

### Qué no queremos

- visor de diffs integrado
- cola de merge
- clon de Jira
- PRs obligatorios para trabajo no-código

### Criterios de aceptación

- Múltiples agentes ingenieros pueden trabajar concurrentemente sin contaminación de workspace.
- Cuando un proyecto está en modo PR, el issue contiene metadatos de rama/worktree/vista previa/PR.
- La vista previa puede reabrirse bajo demanda hasta que expire el TTL.

### No-objetivos

- reemplazar GitHub/GitLab
- hosting universal de vistas previas para cada framework el primer día

## 10) Sistema de plugins como válvula de escape

El roadmap ya incluye plugins, las discusiones de GitHub están activas alrededor de ello, y hay un issue abierto proponiendo un puente SSE específicamente para habilitar UIs de plugins con streaming como chat, logs y monitores. Este es exactamente el lugar correcto para superficies opcionales. ([GitHub][1])

### Decisión de producto

Mantener delgado el núcleo del plano de control; poner experiencias opcionales de alta varianza en plugins.

### Objetivos de plugins first-party

- Chat
- Base de conocimiento / RAG
- Cola de logs / salida de build en vivo
- Trazado personalizado o colas
- Editor de docs / constructor de propuestas

### Manifiesto de plugin

```ts
interface PluginManifest {
  id: string;
  version: string;
  requestedPermissions: (
    | "read_company"
    | "read_issue"
    | "write_issue_comment"
    | "create_issue"
    | "stream_ui"
  )[];
  surfaces: ("company_home" | "issue_panel" | "agent_panel" | "sidebar")[];
  workerEntry: string;
  uiEntry: string;
}
```

### Requisitos de plataforma

- puente de acción host ↔ worker
- streaming de UI/SSE
- auth con alcance de empresa
- declaración de permisos
- slots de superficie en UI

### Criterios de aceptación

- Un plugin puede transmitir eventos a la UI en tiempo real.
- Un plugin de chat puede conversar sin requerir que el chat se convierta en el producto central de Paperclip.
- Los permisos de plugins tienen alcance de empresa y son auditables.

### No-objetivos

- plugins que mutan el esquema central directamente
- ejecución arbitraria de código privilegiado sin permisos explícitos

## Orden de prioridad que usaría

Dado el estado del repo y la transcripción, lo secuenciaría así:

**P0**

1. Seguridad de costos + endurecimiento de latidos
2. Incorporación guiada + primera tarea mágica
3. Base de despliegue compartido/en la nube
4. Artefactos fase 1: adjuntos no-imagen + exposición de entregables

**P1** 5. Superficie de comandos del tablero 6. Capa de visibilidad/explicabilidad 7. Modo auto + interrumpir/reanudar 8. Colaboración multi-usuario mínima

**P2** 9. Ciclo de vida de workspace/vista previa/PR de proyecto 10. Sistema de plugins + plugin opcional de chat 11. Expansión de plantillas/presets para incorporación de startup vs agencia vs equipo-interno

Por qué este orden: el repo actual ya está recibiendo presión en fallas de incorporación, validación de incorporación/auth, aplicación de presupuesto y consumo desperdiciado de tokens. Si eso está tembloroso, todo lo demás se siente impresionante pero inseguro. ([GitHub][3])

## Conclusión

La mejor síntesis es:

- **Mantener** a Paperclip como el plano de control a nivel del tablero.
- **No** hacer del chat, la revisión de código o la construcción de flujos de trabajo la identidad central.
- **Sí** hacer que el producto se sienta conversacional, visible, orientado a salidas y compartido.
- **Sí** hacer de los flujos de codificación una superficie de integración vía enlaces de workspaces/vistas previas/PR.
- **Usar plugins** para bordes más ricos como chat y conocimiento.

Eso mantiene intacta la dirección actual de producto del repo mientras resuelve casi cada dolor expuesto en la transcripción.
